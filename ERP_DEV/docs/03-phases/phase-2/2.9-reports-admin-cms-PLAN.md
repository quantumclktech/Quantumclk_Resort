## 2. reporting-service (D-181)

### 2.1 How data gets in
```
reservation · room · billing · channel · loyalty · operations · guest · lead · access services
        │ events (outbox → Kafka or outbox polling, as fixed in 2.1-A1)
        ▼
reporting-service ── idempotent consumers (event id dedupe) ── reporting_db (facts + dimensions)
        ▲ backfill / rebuild: GET /internal/v1/report-feed?since=…  (each service, paged)
        │
   staff web: dashboards · report catalogue · exports · schedules      "Data as of 10:42" on every page
```
- **Rebuild:** facts can be dropped and rebuilt from the feeds (after a bug fix or a new KPI).
- **Lag monitor:** if the newest event is older than N minutes, an admin alert is raised and the pages show "data delayed".
- **Personal data:** facts store **ids, codes and amounts, not names or contacts**. Names are looked up when a report is opened, based on the viewer's permissions (2.2 field rules). Guest lists drill down into the owning service, which masks fields.

### 2.3 KPI definitions (written once, with tests on fixed sample data)
| KPI | Definition (to be confirmed, Q-117) |
|---|---|

| ADR | net room revenue ÷ paid room nights sold |
| RevPAR | net room revenue ÷ available rooms (total − OOO) |
| ALOS | average nights per stay |
| Cancellation / no-show rate | cancelled (no-show) bookings ÷ bookings for the period, by arrival date |

### 2.5 Exports
- **CSV** (streamed), **Excel `.xlsx`** (Apache POI, a new dependency in the ADR, with formatted headers and totals) and **PDF** (the same PDF library as the 2.5 invoices, resort header, filters printed, "generated by / at").
- Large exports run as a **background job** and give a download link that expires.
- Every export is **audited** (who, which report, filters, row count). Exports holding personal data need `guests.export` on top of `reports.export`.

### 2.7 Scheduled reports (D-183)
- `report_schedule`: report, saved filters, format, schedule (after the night audit / weekly day + time / monthly day), recipients (**staff accounts only**), owner, active.

- `report_delivery` log with retries. Failures appear on the admin health page.

## 4. content-service + CMS (D-182, ERP-01)

### 4.1 Content model
| Content | Notes |
|---|---|
| `page` + `page_version` | fixed columns (slug, **locale**, status, title, SEO meta, OG image, published_at, version) + a **`blocks` JSONB array**. Every save is a `page_version` row (rollback/diff). See ADR-004 §C |
| Blocks | typed blocks (hero, richText, gallery, roomFacts, offerCard, faq, cta). **Each block type has a versioned JSON Schema**: validated on save (invalid → 400, never stored); each block carries `"v"`, so old versions still render; a new schema version comes with its renderer (+ a stored-block migration if needed) |
| Rich text | stored as a **structured JSON document** (allow-listed nodes/marks: paragraph, h2–h4, lists, bold, italic, link, quote), **never raw HTML**. The site renders it with escaping and only `https:`/`mailto:`/internal links; pasted HTML is converted to allowed nodes, the rest dropped. Stops stored XSS |
| Room-type content | description, image set, amenity list, display order. **Facts (occupancy, bed, count) come from room-service (2.3)**, so they are never typed twice |
| Packages / offers | title, description, valid dates, price text or a link to a 2.1 rate plan, call to action (book / enquire) |
| Gallery | albums, images with **alt text required** |
| Banners | placement, start/end schedule, link |
| Blog / announcements | posts, publish date, tags, author |
| Site settings | contact details, social links, map, footer, desk phone (+91 8353 200 100 used in D-142) |
| Membership page | text from the CMS; booklet balances/benefits live from loyalty-service (2.7) |

### 4.2 Media library
Upload JPEG/PNG/WebP/AVIF (checked by magic bytes, ≤ 15 MB) → **EXIF data removed** → **sha256 de-duplication** (the same bytes stored once; every reference points to one `media_asset`) → variants WebP/AVIF 480/960/1600 px → **alt text required before publishing** → stored under a hash-based key in object storage (local volume in dev; production storage decided in 2.10). `media_asset`: sha256, mime, size, dimensions, alt text, variants, storage key.
- **Two buckets (ADR-004 §C.4):** `public-media` (website images, served through Caddy/CDN with long cache and hash-based URLs) and `private` (ID scans, payment proofs, invoices: **app-encrypted AES-256-GCM**, downloaded only through the API after a permission check, never a public URL).
- A file still used by a published page can't be deleted. Unreferenced files are removed by a cleanup job after a grace period.

### 4.3 Workflow
- **DRAFT → IN_REVIEW → PUBLISHED / ARCHIVED.** Scheduled publish. Every save is a **version**, with a diff and one-click **rollback**.
- **Preview** through a signed link that shows the draft on the real site layout.
- Permissions: `cms.edit`, `cms.publish` (reviewer ≠ author is a setting), `cms.media_manage`. Who does what: Q-120 / Q-015.

### 4.4 Website integration
- The Next.js site reads **published** content from the public read API (cached).
- On publish, content-service calls a **signed revalidation webhook**, and only the affected pages are rebuilt. If the API is down, the site keeps showing the last good content.
- **Migration:** the current hard-coded content (`stay-data.ts`, `membership-data.ts`, dining, experiences, gatherings, home) is loaded into the CMS as the first version. **The "to be confirmed" marks are kept**, so unconfirmed text stays visibly unconfirmed until the client approves it (Q-121).
- **SEO:** meta tags, sitemap.xml and robots.txt generated from published pages, basic Hotel structured data.
- **Basic analytics** (SOW ERP-01): provider and **cookie/consent banner** per Q-122 (DPDP).
- **Enquiry management:** website enquiries stay in the lead flow (lead-service). An **event enquiry** type (banquet/wedding/corporate, SRS §3.2, Q-008/Q-124) is added to the form and routed to sales.

### 4.5 Staff screens (Content area)

## 8. Verification (when executed)
1. **KPIs:** a fixed 7-day sample (bookings, OOO, comps, cancellations) gives the expected occupancy, ADR, RevPAR, ALOS and source mix to the paisa. Business-date boundaries are tested in IST.
2. **Read models:**
   - the same event replayed 5× → counted once;
   - drop and rebuild from the feeds → identical totals;
   - stop consumers → the "data delayed" banner and an admin alert appear.
3. **Totals match the source:** the revenue report total = billing's invoice totals for the same period (excluding tax); outstanding = billing's AR.
4. **Exports:** CSV/Excel/PDF give the same totals as the screen; a 100k-row export runs as a background job; every export is in the audit; a guest-list export without `guests.export` → 403.
5. **Schedules:** the daily report is sent after the night audit; a report with personal data is sent as a sign-in link, never an attachment; a failed send is retried and shown on the health page; a non-staff recipient can't be added.
6. **Settings & flags:** a change shows before/after in the audit; a module switched off by flag is refused on the server (403/404), not only hidden.
7. **CMS:**
   - draft → review → publish → the site page updates within seconds (revalidation);
   - rollback restores the previous version;
   - an image without alt text can't be published;
   - an invalid block (fails its JSON Schema) → 400 and nothing stored; a page saved with `hero v1` still renders after `hero v2` exists;
   - rich text with a pasted `<script>`, `onerror=` or `javascript:` link is stored without it and renders as plain text;
   - uploading the same image twice → one `media_asset`; a private file has no public URL and returns 403 without permission;
   - EXIF is removed;
   - the preview link expires;
   - if the API is down, the site still shows the last good content.
8. **Migration:** every current site page shows the same content after the move, and the "to be confirmed" marks are still present.
9. Permission tests for every endpoint. All service tests, web and landing tests, lint and build pass.
