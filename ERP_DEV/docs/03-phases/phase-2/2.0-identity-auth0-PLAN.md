- Status: **Plan approved by Ashish on 2026-11-28 (docs only).** No code yet. **Updated 2026-11-28:** staff onboarding & login flow with welcome email, self-set password and OTP by role (§2A, D-189…D-192) and the Phase 1 weak-spot fixes (§2B, D-193); this section is awaiting Ashish's review. - Affects plans: [2.2 RBAC](2.2-rbac-PLAN.md) (role bundles move to Auth0 RBAC), [2.6 booking + CRM](2.6-booking-engine-crm-PLAN.md) (guest sign-in), and everything built in Phase 1 that uses Keycloak.

## Context

Ashish asked to "implement OAuth instead of Keycloak". **Keycloak is already an OAuth 2.0 / OpenID Connect server.** What he chose is to **replace Keycloak with Auth0 (by Okta)**, a hosted OAuth 2.0 / OIDC service, and to **add Google sign-in**. His reason: *"Want full control / learning."*

> ⚠ **Trade-off, recorded honestly:** Auth0 is a **hosted** service. Login pages, password storage, token signing and brute-force protection run on Okta's servers and are set through its dashboard and API. Compared with Keycloak we get **less** control over the identity server itself, but much less to run and operate. What stays fully ours: token checks in every service, roles and permissions design, scopes, approvals and audit (2.2).

**What Keycloak does today, all of which must be replaced:**

| Area | Built in Phase 1 | Where |
|---|---|---|
| Staff login | realm `gh-staff`, client `erp-web` (code + PKCE S256), API audience `erp-api`, themed sign-in pages | `infra/keycloak/gh-staff-realm.json`, web `auth.ts` (`keycloak-js` 26.2.5) |
| Guest/member login | realm `gh-guests`, audience `guest-api`, remember-me 30 days (D-127), themed pages | `gh-guests-realm.json`, landing `guest-auth.ts`, `guest-session.ts` |
| Roles and permissions | realm roles ADMIN / MANAGER / SALES_EXECUTIVE = composites of `erp-api` client roles; token claims `realm_access.roles`, `resource_access.erp-api.roles` (D-146) | realm JSON, `SecurityConfig.authenticationConverter()` in access, lead and guest services, gateway |
| Employee accounts | create user, assign role, invite email (VERIFY_EMAIL + UPDATE_PASSWORD), enable/disable, log out, status sync, bootstrap ADMIN | access-service `KeycloakAdminClient`, `AccountService`, `AccountJobs` (28 files mention Keycloak) |
| Member accounts | create guest user, **custom extension `gh-member-activation`** (one-time set-password link, then auto sign-in), welcome email, resend | guest-service (11 files), `infra/keycloak-extensions`, `keycloak-providers/*.jar` |
| User id in our DBs | `employee.keycloak_user_id UUID`, `guest_account.keycloak_user_id UUID PRIMARY KEY` | V1 migrations |
| Infra | Keycloak 26.8.2 container, `keycloak` DB, Caddy route, `check-stack.ps1`, Testcontainers Keycloak tests | `infra/`, tests |

## 1. Decisions (D-166 … D-169)

| ID | Decision | Why |
|---|---|---|
| D-166 | **Auth0 replaces Keycloak for both staff and guests.** Staff and guests stay separate: separate **database connections**, separate **applications** and separate **APIs** (audiences `erp-api` and `guest-api`), so staff and guests never share roles (Blueprint §3). Role bundles move from Keycloak composites to **Auth0 RBAC** (roles → API permissions, `permissions` claim in the access token). **Supersedes ADR-002** and changes the storage part of **D-146**. The rest of 2.2 (scopes, approvals, audit, catalogue, temporary grants) is unchanged. | Ashish's choice (Auth0 + Google). One identity system to run. |
| D-167 | **Google sign-in for guests only.** Guests and members may use Google or email + password. **Staff use only database accounts created by the Admin.** No Google sign-in for staff, so a personal Gmail can never get into the ERP. | Ashish chose the recommended option. |
| D-168 | **Direct replacement.** Keycloak code is replaced by Auth0 code (Auth0 SDKs and the Management API). There is no provider-neutral layer and no period where both run side by side. Rollback = restore the last pre-switch release and DB backup (§7). | Ashish's choice (faster). Accepted risks: tied to Auth0, and no gradual rollback (R-new, §9). |
| D-169 | **One Auth0 tenant per environment** (dev, staging, production). Each tenant holds both the staff and the guest setup. Tenant config is **kept as code** in the repo (Auth0 Deploy CLI export, **no secrets**), reviewed in PRs. | Ashish chose the recommended option. Test users never mix with real ones, and settings can be reviewed and repeated. |

**Blueprint deviation:** Blueprint ADR-006 says "Keycloak using OAuth2/OIDC". This plan changes the product but keeps OAuth2/OIDC. It is recorded in the new ADR (unit I1). It is not a scope change: the SOW asks for secure role-based authentication, not a named product.

## 2. Target design (per tenant)

```
Auth0 tenant  (dev | staging | prod; custom domain e.g. login.<resort-domain>, Q-091)
├─ Database connection  "staff-db"     → signup DISABLED (Admin creates accounts), password policy, brute-force protection, MFA for ADMIN (Q-095)
├─ Database connection  "guests-db"    → signup enabled (website), email verification required
├─ Social connection    "google-oauth2"→ enabled for the WEBSITE app only (D-167); resort-owned Google OAuth client (Q-092)
├─ Application "erp-web"      (SPA, code + PKCE, refresh-token rotation)   ← staff-db only
├─ Application "guest-web"    (SPA, code + PKCE, refresh-token rotation)   ← guests-db + google
├─ Application "access-svc-m2m" / "guest-svc-m2m" (machine-to-machine → Management API, least scopes)
├─ API "erp-api"   (RBAC on, "add permissions in the access token" on; RS256)
├─ API "guest-api" (no staff permissions)
├─ Roles  ADMIN, MANAGER, SALES_EXECUTIVE (+ 2.2 roles as built) → permissions of erp-api
└─ Actions (post-login)
    ├─ add namespaced claims: https://goldenhills/roles, …/property_id, …/departments (2.2 §6)
    ├─ deny staff login if the ERP employee is not ACTIVE (block flag is the main control)
    └─ guests: link a Google identity to an existing guests-db user with the same VERIFIED email (D-164 sure match)
```

**How tokens are checked in every service** (resource-server code stays Spring Security; only the configuration and the claim mapping change):
- issuer `https://<tenant-domain>/` (trailing slash), JWKS `/.well-known/jwks.json`, RS256, audience `erp-api` or `guest-api`, expiry with the existing 60 s skew;
- converter: `permissions` → `PERM_x`; `https://goldenhills/roles` → `ROLE_x`; property/department claims → the 2.2 `Scope` helper;
- the 401/403 JSON errors and the check order (AUTHENTICATION §3) are unchanged.

**Session rules** (map the current behaviour):

| Today (Keycloak) | Auth0 setting |
|---|---|
| Access token 5 min | API token lifetime 300 s |
| Refresh rotation | refresh-token rotation + reuse detection, inactivity/absolute lifetimes |
| Staff: tokens in memory only | SDK `cacheLocation: 'memory'` |
| Guests: remember-me 30 days (D-127, Q-034) | guest-web session/refresh lifetimes 30 days |
| Role change → logout | revoke the user's refresh tokens and sessions through the Management API; the access token expires in ≤ 5 min |

## 2A. Staff onboarding & login flow (added 2026-11-28, D-189 … D-193)

Ashish asked for: an email saying "you've been added as an employee for this role", a link to the ERP login, email + password, and a one-time OTP. It is designed the way real companies do it. **Nobody ever sends or knows the employee's password**, and there is **one login page** for all roles.

### Step by step
```
 1 Admin adds employee ──► 2 Welcome email ──► 3 One-time link ──► 4 Employee sets ──► 5 ERP login ──► 6 OTP setup ──► 7 Role dashboard
   (name, email, mobile,     "You've been        (Auth0 password-    own password       (email pre-      (first login
    PAN, job role)            added as <Role>"    change ticket,      (policy shown)     filled)          only)
                                                  72 h, single use)
```
1. **Admin creates the employee** (unchanged form). access-service creates the Auth0 `staff-db` user (random unknown password, `email_verified=false`) and assigns the Auth0 role. Status `PENDING_PROVISIONING` → `INVITED`.
2. **Welcome email** is sent by *our* notification-service through the resort's SMTP (Gmail SMTP in dev/now, resort domain later, Q-093). It has the Golden Hills design and this content:
   *"Hi {first name}, you've been added to the Golden Hills ERP as **{Role display name}** by {Admin name}. Set your password to get started. This link works once and expires in 72 hours."* + a **Set your password** button. It contains **no password and no OTP**.
3. **The link** is an Auth0 **password-change ticket** (`ttl_sec = 259200`, `mark_email_as_verified = true`, `result_url = <ERP>/erp/?login_hint=<email>`). It works once. Opening an expired or used link shows "Ask your Admin to resend". The Admin sees **Invite expired → Resend** (resend creates a new ticket; the old one is dead; max 3 per hour, unchanged).
4. **The employee sets their own password** on the Golden Hills-branded Auth0 page (password policy shown: Q-026 default of 12+ characters, no reuse of the last 5).
5. **They land on the one ERP sign-in page** (`/erp/`). The email is pre-filled (`login_hint`). They enter their password. There is **no per-role login page** (D-192): the role comes from the token, never from the URL.
6. **OTP (MFA) on the first login** (D-190), enforced by the post-login Action based on the user's role:

   | Role | OTP method | Asked when (D-191) |
   |---|---|---|
   | ADMIN | **Authenticator app** (TOTP: Google/Microsoft Authenticator), with recovery codes | **Every login** + again before risky actions (step-up) |
   | MANAGER | **Authenticator app** (TOTP), with recovery codes | New device / browser, or after 7 days |
   | SALES_EXECUTIVE (and other staff roles from 2.2 unless set otherwise) | **Email OTP** (6-digit code to their work email) | New device / browser, or after 7 days |

   First login = enrolment (QR scan for the app; a code to the email for email OTP). Recovery codes are shown once. If an employee loses their phone, the Admin presses **Reset OTP** (audited, with a reason): the factor is removed and enrolment is asked for again on the next login.
7. **Role dashboard.** `/me` returns the role and modules. The ERP opens that role's home screen (Sales Executive → Memberships, Admin → Employees, Manager → Verification queue, as today).

Status shown to the Admin: `INVITED` → `PASSWORD_SET` (ticket used) → `ACTIVE` (first login with OTP done) ↔ `DISABLED`, plus `INVITE_EXPIRED` and `INVITE_EMAIL_FAILED` with Resend.

### Step-up for risky actions (D-191)
Deactivate / reactivate, role change, Reset OTP, bootstrap/last-admin operations and (later, 2.2) permission grants need a **fresh OTP from the last 5 minutes**. The ERP asks for it through `loginWithRedirect({ acr_values: MFA, max_age: 300 })`. The backend checks the token's `amr` contains `mfa` and `auth_time` is ≤ 300 s old, otherwise **401 `step_up_required`**, which the web app handles by asking for the OTP.

### Every later login
Email + password → OTP (if the device rule asks) → role dashboard. Wrong password or OTP: Auth0 brute-force protection (lock after 10 tries, unlock by email) + our gateway rate limit.

### To confirm in unit 2.0-I1 (dev tenant spike, before coding)
- That the Auth0 plan chosen in Q-090 includes **email OTP and TOTP** factors, per-role enforcement from an Action, and "remember browser" with a **7-day** lifetime. If email OTP is not available as the only factor for Sales Executives, the fallback is TOTP for them too (ask Ashish).
- Password-change ticket TTL and `result_url` behaviour.

## 4. RBAC in Auth0 (changes the storage part of 2.2 §1/§8)
- **Permissions** = API permissions on `erp-api`, with the same names as today (`employees.read`, `leads.claim`, `memberships.verify`, …) and the 2.2 catalogue as it is built.
- **Job roles** = Auth0 roles holding those permissions (same codes as 2.2 §3). A user can hold several (Q-055).
- **Temporary grants (2.2 D-148):** assign a **single-permission role** or a direct user permission through the Management API. The existing expiry job removes it. The audit stays in access_db.
- **Custom roles:** created through the Management API with the subset rule checked in access-service.
- **Baseline as code + drift check:** the role → permission baseline lives in `infra/auth0/` (Deploy CLI format). The nightly job compares the live tenant with it (2.2 R5).
- **Token size:** Auth0 adds every permission of the user's roles to the access token. Measure in I3 (same check as 2.2 R1).

## 5. Google sign-in (guests, D-167)
- A Google OAuth client is created in a **Google Cloud project owned by the resort/QuantumCLK** (not Auth0's shared dev keys, which are dev only), with the consent screen branding and verification (Q-092).
- Scopes: `openid email profile` only.
- **Account linking:** a Google sign-in whose **verified** email equals an existing `guests-db` user → linked by the post-login Action, one person = one guest account (D-164). An unverified email → no link, a separate account, and a CRM suggestion.
- Members (Gold) may sign in with Google once linked. The member's welcome flow still sets a password first, so email always works.
- The staff ERP application never enables the Google connection (tested).

## 7. Cutover runbook (direct replacement, D-168)
1. Dev tenant built from config-as-code; all services and both web apps pass their tests on the dev tenant.
2. Staging tenant + staging deploy; full regression (§10); a run-through of the migration with a copy of the user export.
3. **Release freeze → backup** of access_db, guest_db and the `keycloak` DB → export users → import into the production tenant → run the id-mapping script → deploy the Auth0 release → smoke test (staff sign-in per role, member sign-in, Google sign-in, invite, deactivate).

## 11. Verification (when executed)
1. **Tokens:** every service rejects a missing, expired, wrong-issuer or wrong-audience token, and a token signed by an unknown key (401). A guest-api token on a staff path → 401, and the reverse. Same tests as REQ-IAM-007, now on the new issuer.
2. **RBAC:** each role signs in and gets exactly its permissions in the token. `/me` and the menu match. A missing permission → 403. The drift check flags a manual dashboard edit.
3. **Staff lifecycle:** Admin creates an employee → invite email (Mailpit in dev) → set password via the ticket → sign in → deactivate → the next refresh fails, access ends within ≤ 5 min → reactivate. Last-ADMIN guard still holds.
4. **Members:** verify a Gold Member → welcome email with Member ID → set password → signed in on the website → card shown. Resend makes a new ticket; the old link no longer works.
5. **Google:**
   - a guest signs in with Google → account created;
   - an existing guest with the same verified email is **linked, not duplicated**;
   - the staff ERP shows no Google button, and a Google identity can't get an `erp-api` token.
6. **Security:**
   - no password grant (only code + PKCE);
   - redirect/callback URLs only for the listed origins (localhost, ngrok, VPS: D-143);
   - brute-force lockout works;
   - MFA enforced for ADMIN if Q-095 says so;
   - no secrets in the repo (secret scan).
7. **Migration rehearsal on staging:** imported users sign in (or receive reset emails); every old id is mapped; audit history still readable.
8. All service tests, web and landing tests, lint and build pass **without internet** (local JWKS + WireMock).
9. **Staff onboarding & OTP (§2A):**
   - the welcome email names the role and holds no password or OTP;
