## Context

**Where things stand:**
- The website (`landing-page/`) has room pages and a *Plan your stay* portal. Its "Reserve" tab only sends an **inquiry** to the sales desk (`plan-stay-portal.tsx`). Fake confirmations were removed in D-142.
- Guests sign in through Keycloak realm `gh-guests`. `guest-service` (`guest_db.guest_account`) holds only the account link: email, name, mobile and source.
- There is **no central guest profile, no stay history, and no way for a guest to book and pay online**. SOW ERP-02 and ERP-04 both need these.

**Client facts:**
- Booking channels: website, phone/walk-in, WhatsApp, OTA and agents.
- Both direct booking and enquiry should be possible.
- Promo codes: the client said both "not allowed" and "allowed" (C-03).
- A waitlist was mentioned but not confirmed (C-12), so it is not in the baseline.
- SMS is excluded (SRS §11.2), so email is the verification channel (Q-007).

## 1. Decisions (D-162 … D-165)

| ID | Decision | Why |
|---|---|---|
| D-162 | **Sign-in is required to book online.** A guest must have a `gh-guests` account with a **verified email** before paying. New guests register in the same flow (the existing Keycloak registration and email verification). The search and its selection are kept through the sign-in redirect, so the guest returns to the same step. | Ashish chose this over guest checkout: every booking is tied to a verified person, and booking history and the CRM link are always right. |
| D-163 | **Instant booking only up to a limit:** up to **N rooms** (placeholder 3) and **M nights** (placeholder 14) per booking, for sellable room types only. Larger groups, events, the dormitory and special requests still go to the **existing inquiry → lead flow**, with the search pre-filled. | Ashish chose the recommended option. Keeps group and event pricing with the sales team. |
| D-164 | **Duplicate guests:** link automatically only on a **sure match**: a verified email, or the same ID-document hash. Likely matches (same mobile, similar name + date of birth) are only **suggested** to staff, who merge by hand. Merges are audited and can be undone. OTA proxy emails never count as a match. | Ashish chose the recommended option. Avoids wrong merges from shared family phones and OTA relay addresses. |
| D-165 | **No member-only prices on the website for now.** Everyone sees the public rate plans. Member pricing moves to the loyalty plan (2.7) once the client confirms membership benefits. | Ashish chose "Not now". Benefits aren't settled, so no price is invented. |

## 2. Part A — Booking engine (website + reservation-service)

### 2.1 Guest journey (SOW ERP-02 workflow)
```
Stay page / "Book now"
  → 1 Search: dates, adults, children (ages), rooms
  → 2 Results: available room types with nightly price, total, taxes, policy summary,
       "Only 2 left" (optional, Q-082); unavailable types shown greyed with next free dates
  → 3 Choose: room type × count, rate plan / meal plan (EP/CP/MAP… as configured in 2.1)
  → 4 Sign in / register (D-162) — returns to step 4 with the selection kept
  → 5 Guest details: lead guest (prefilled from the profile), names of other adults,
       arrival time, special requests, GSTIN for a company invoice (optional)
  → 6 Review: price breakdown per night, taxes (billing quote), advance due now, balance due,
       cancellation policy text, terms + privacy acceptance (stored with version and time)
  → 7 Pay advance: billing hosted checkout (2.5 §5.2) — room held until the hold expires
  → 8 Confirmation page + email (reference, dates, room type, paid, balance, policy, manage link)
  → My bookings (/profile): view, pay balance, cancel (with refund quote), request a change, download invoice
```
Over the D-163 limits, or for the dormitory or an event, step 2 offers **"Send an inquiry"** instead, which uses the existing lead flow with the search pre-filled.

### 2.2 Server rules
| Rule | How |
|---|---|
| **Price comes from the server** | `POST /portal/bookings` works out the price again from 2.1 rates + restrictions + billing tax quote. A **quote id** is locked for the hold time. The amount sent to the gateway always comes from the server. |
| **No double booking** | The booking becomes a 2.1 **HOLD** (stock taken in the locked transaction) with an expiry (Q-076, placeholder 30 min). Paid → CONFIRMED. Expired → released (2.5 §5.2). |
| **Restrictions** | Minimum/maximum length of stay, closed to arrival/departure and stop-sell (2.1) are applied in search and again at hold time. |
| **Abuse limits** | Rate limits per IP and per account (gateway Redis). **At most 2 open holds per account.** Hold expiry. Idempotency-Key on create. (A captcha is a new dependency that needs approval; it is added only if abuse appears.) |
| **Self-cancel** | `GET …/cancellation-quote` shows the fee from 2.5 `cancellation_policy`. Confirm → reservation CANCELLED → stock released → billing posts the fee and refunds the rest automatically to the original method (approval rules for automatic policy refunds: Q-081). |
| **Changes** | Version 1: **"Request a change"** goes to the desk as a task. The desk changes the booking with the 2.1 rules. Self-service date changes only if the client wants them (Q-086). |
| **Promo codes** | Supported **but OFF by default** (C-03, Q-084). Rules: code, %/amount, valid dates, stay dates, blackout dates, min nights, room types, usage limit per code and per guest. Changes are audited, and the discount is checked on the server. |
| **OTA parity** | The website uses the same 2.1 stock and rates, so a website booking reduces OTA availability straight away (2.1 ARI push). |

### 2.3 APIs (reservation-service portal chain: `gh-guests` tokens, aud `guest-api`, same pattern as the access-service portal chain)
| Endpoint | Auth |
|---|---|
| `GET /api/v1/portal/availability?from&to&adults&children&rooms` | public, rate-limited |
| `GET /api/v1/portal/room-types` (2.3) | public |
| `POST /api/v1/portal/quotes` → quoteId, lines, taxes, advance | public, rate-limited |
| `POST /api/v1/portal/bookings {quoteId, guests, requests, consentVersion}` + Idempotency-Key → HOLD + payment session | guest token, **email verified** |
| `GET /api/v1/portal/bookings`, `/{ref}` | guest token (own bookings only, else 404) |
| `GET /{ref}/cancellation-quote`, `POST /{ref}/cancel`, `POST /{ref}/pay-balance`, `POST /{ref}/change-request`, `GET /{ref}/invoice` | guest token, own booking |
| `POST /api/v1/portal/promo/validate` | guest token |

### 2.4 Emails (minimal `notification-service`, the email adapter planned in ARCHITECTURE §3)
- Booking confirmation, payment receipt, cancellation confirmation, refund status, and a pre-arrival reminder (optional, a setting).
- Templates with the resort branding. Sent from the resort's domain (SPF/DKIM, Q-085). Mailpit in dev.
- Every send is recorded as a **communication record** in the CRM (§3.3). WhatsApp is only added if ERP-12 is confirmed.

### 2.5 Website screens (landing page, Next.js)
Search bar on the home and stay pages · results page · booking steps 3–8 · **My bookings** in `/profile` (upcoming / past, actions) · booking detail · inquiry fallback. These follow the existing site design (`mobile.css`, `booking-dates.ts` date validation from D-141). They use no fake data: on an error the site shows the desk number, as in D-142.

### 2.6 Booking reports (staff; full reporting comes in a later plan)
Bookings by source/channel, pickup (bookings made per day for future dates), cancellations + reasons, lead time, online conversion (searches → holds → paid), expired holds.

## 3. Part B — Guest CRM (guest-service, ERP-04)

### 3.1 Data model (`guest_db`, new tables next to `guest_account`)
| Table | Purpose |
|---|---|
| `guest_profile` | **the central guest record**: id, names, date of birth (optional), nationality, address, company, VIP flag, tags, status ACTIVE / MERGED (→ into id) / ANONYMISED, created_from (WEBSITE, OTA, WALK_IN, PHONE, MEMBERSHIP, STAFF) |
| `guest_account.profile_id` | links the existing Keycloak account (optional; walk-in and OTA guests may have none) |
| `guest_contact_point` | email or mobile, normalised value, verified, source, primary. **OTA relay addresses** (e.g. `*@guest.booking.com`) are marked `proxy`, never used for matching |
| `guest_id_link` | **ID-document HMAC hash only** (from 2.4 registration), id_type. Used for sure matches. Never the number |
| `guest_preference` | category ROOM (floor, bed, quiet, view), FOOD (veg, Jain, allergies), OCCASION (birthday, anniversary), OTHER; value; source (guest / staff); updated_at |
| `guest_note` | staff notes, visibility (all staff / managers), author. Shown as an alert on arrival if flagged |
| `guest_communication` | channel EMAIL / WHATSAPP / PHONE / IN_PERSON, direction, subject, short summary, related booking, by, at. Automatic for system emails; added by hand for calls |
| `guest_consent` | purpose (booking terms, privacy policy, marketing email, marketing WhatsApp), version, granted/withdrawn, at, source. **Append-only** (DPDP proof) |
| `guest_stay_summary` | read model fed by events: bookings, stays, nights, no-shows, cancellations, last stay, lifetime revenue (from `FolioSettled`), membership ref. Used for **returning guest recognition** |
| `merge_candidate` / `merge_log` | suggested pairs with score + reason; merges keep the data needed to **undo** |
| `audit_event` (exists) | profile edits, merges, consent changes, data requests |

D-120 still holds: guest_db stores **no passwords and no membership details**, only a membership reference id.

### 3.2 Matching and recognition (D-164)
| Match | Action |
|---|---|
| Verified email equal (not a proxy) | **auto-link** to the profile |
| Same ID-document hash | **auto-link** (needs the same HMAC key in reservation-service and access-service: one shared secret, `IDENTITY_HASH_KEY`, set in the ADR) |
| Same normalised mobile | **suggest** |
| Name similarity + same date of birth or same address | **suggest** |
| OTA proxy email only | no match; new profile, suggestions only |

**Recognition:** when a reservation is created, imported from an OTA (2.1) or registered at the desk (2.4), reservation-service calls `POST /internal/v1/guests/resolve {email?, mobile?, idHash?, name}`. It gets back a profileId and **badges**: Returning (N stays), VIP, Member, Preferences, Note alert. The arrivals list and the booking screen show the badges.

### 3.3 Communication records
System emails (§2.4) are logged automatically through a `NotificationSent` event. Staff log calls and in-person conversations by hand. Shown on the guest's timeline.

### 3.4 Privacy (DPDP)
- Consent is captured at booking and registration (versioned text from the client, Q-083/Q-087). Marketing consent is **off by default**.
- **Data requests:** a guest can ask for a copy of their data (export) or for erasure. Erasure **anonymises** the profile (names, contacts, preferences, notes), but **financial and legal records are kept** as the law requires (invoices, registration for the required period, Q-088). Handled by staff with `guests.privacy_manage`. Audited.
- Minimal fields per role (2.2 §6): housekeeping sees name + room + flagged notes only. Mobile and email are masked in lists unless the role needs them.

### 3.5 Staff screens
| Screen | Content |
|---|---|
| **Guest search** | by name, mobile, email, booking ref, membership no., room. Fast fuzzy search (Postgres `pg_trgm`: an extension that needs approval in the ADR) |
| **Guest 360** | profile, contacts, badges, preferences, notes, booking and stay history, folio totals (from 2.5), membership link, communications, consent log |
| **Merge queue** | suggested duplicates side by side, merge / not the same person, undo from the merge log |
| **Data requests** | export / erasure requests and their status |

### 3.6 Guest-facing (website `/profile`)
My details (edit name, mobile, address), preferences (self-edit), marketing consent switches, my bookings (Part A), invoices. All of it through `gh-guests` tokens; a guest can only ever see their own data.

## 8. Verification (when executed)
1. **Booking safety:**
   - 20 guests race for the last room online → exactly one HOLD;
   - an expired hold releases the room;
   - a client-sent price is ignored;
   - a website booking drops OTA availability (2.1 mock).
2. **Sign-in rule:** booking without a verified email → 403. After sign-in the guest lands on the same step with the selection kept.
3. **Limits:** 4 rooms (over N) → inquiry offered, no hold; a third open hold on the same account → refused.
4. **Self-cancel:** quote = the policy fee; cancel → stock released, fee posted, rest refunded on the mock gateway; a guest can't see or cancel someone else's booking (404).
5. **Matching:**
   - the same verified email from website and walk-in → one profile;
   - the same mobile only → a suggestion, not a merge;
   - an OTA proxy email never merges;
   - undoing a merge restores both profiles.
6. **Privacy:** erasure anonymises the profile but keeps invoices; the consent log is append-only; housekeeping sees no contact details.
7. **Emails:** confirmation in Mailpit with the correct amounts; a failed send is retried and shown in the delivery log; each send appears on the guest's timeline.
8. **End to end on mocks:** search → sign in → pay advance (mock) → confirmation email → profile shows the booking → check-in at the desk shows the "Returning" badge on the second stay.
9. All service tests, web and landing tests, lint and build pass.
