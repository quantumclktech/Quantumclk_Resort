## 3. Production topology (D-184)

```
Internet ──443──► Caddy (TLS, HSTS, security headers, rate limits, body limits)
                    ├─ www.<domain>      → landing (Next.js)
                    ├─ erp.<domain>      → staff web (static)
                    ├─ api.<domain>      → api-gateway → services (internal Docker network only)
                    └─ webhooks          → payment gateway / terminal / channel manager callbacks (via gateway)
login.<domain> → Auth0 custom domain (2.0, Q-091)
Monitoring UI (Grafana) → only through an IP allow-list or VPN
Postgres · Redis · Kafka · Prometheus · Loki → internal network only, no public ports
```

**Minimum VPS size (to confirm with a load test in N8):**

| Item | Production | Staging |
|---|---|---|
| vCPU | 8 | 4 |
| RAM | **32 GB** (services ~13–16 GB, Postgres 4–6 GB, Kafka 2 GB, monitoring 2 GB, headroom) | 16 GB |
| Disk | 200 GB NVMe SSD (DB, WAL, media, logs) | 100 GB |
| OS | Ubuntu LTS, Docker Engine + Compose v2 | same |

Every container has memory/CPU limits, a health check and `restart: unless-stopped`. Postgres is tuned for the RAM. Media files live on a volume that is backed up (§5).

## 4. Security hardening (SOW §25.2)

| Layer | Measures |
|---|---|
| **OS** | unattended security updates; SSH **keys only**, no root login, a separate `deploy` user; firewall (ufw): only 80/443 public, SSH from an allow-list; fail2ban; time sync; disk encryption if the provider offers it |
| **Containers** | non-root users, read-only filesystems where possible, no Docker socket in containers, images pinned by digest, **Trivy image scan** and an **SBOM** in CI |
| **Network** | an internal Docker network; databases and brokers never published; CORS strict per origin (D-143) |
| **TLS / web** | Let's Encrypt via Caddy, HSTS, CSP and other security headers for the web and landing, secure cookies |
| **Secrets** | per-environment env files (root-only, 600) or Docker secrets; never in the repo (gitleaks already in CI); a rotation runbook (gateway, terminal, M2M, RFID master key, DB) |
| **Database** | the existing least-privilege user per service; no superuser for apps; TLS inside the host is optional; encrypted backups |
| **Application** | the validation, rate limits, RBAC and audit already in the plans; **OWASP ZAP baseline scan** on staging in CI; the permission test matrix (2.2-R8); dependency review (exists) |
| **Privacy (DPDP)** | privacy notice updated (Auth0 region, analytics, Q-083/Q-094/Q-122); retention jobs (ID scans, health notes, payment proofs); a **data breach response runbook** (who decides, who informs, within what time) |
| **Payments (PCI)** | hosted checkout and terminal only, so the scope is the smallest self-assessment level. Card data never touches the servers (2.5) |
| **Before go-live** | an OWASP Top-10 checklist review and a light penetration test on staging (Q-135) |

## 5. Backup and disaster recovery (D-185, SOW §25.3)

| What | How |
|---|---|
| Postgres (all service DBs) | **pgBackRest or WAL-G** (chosen in the ADR): nightly full + continuous WAL archiving to **off-site S3-compatible storage**, encrypted, 30 days, object lock where offered |
| Media (CMS images, payment proofs, ID scans) and config | **restic**, nightly, encrypted, off-site. Retention follows each data type's rules |
| Monitoring | backup success/failure and WAL archive lag are **alerted** (§6). Daily backup status on the admin health page (2.9) |
| **Monthly restore test** | automated: restore to a **throwaway isolated VM**, run checks (row counts, latest booking time, a sample invoice), then **destroy it**. The result is logged. Production data never goes to staging |
| **Recovery procedure** (SOW deliverable) | step-by-step runbooks for three cases: **point-in-time restore** (e.g. a bad migration or deletion), a **whole VPS lost** (new VPS from the provisioning scripts + restore, target ≤ 4 h), and **ransomware or account compromise** (restore from object-locked copies, rotate all secrets) |
| Pre-deploy | every production deploy takes a fresh backup first (D-187) |

## 6. Monitoring and alerts (D-186)

- **Metrics:** Spring Actuator/Micrometer from every service, node exporter, Postgres exporter, cAdvisor.
- **Logs:** structured JSON with the correlation id (already the rule), shipped to Loki. **Personal data is scrubbed** (no ID numbers, tokens or card data; this already holds).
- **Dashboards:** service health; HTTP rate, errors and latency; JVM; database; **business signals** (bookings per hour, payment failures, OTA sync DLQ, event lag, night audit status).
- **External uptime check** of the website, ERP, API health and webhook endpoints, from outside the VPS.

**Alerts** (email + an on-call messaging channel, Q-128):

| Alert | Fires when |
|---|---|
| Service down / not healthy | 2 min |
| 5xx rate above threshold, latency p95 above threshold | 5 min |
| Disk > 80 %, memory pressure, container restarts looping | immediately |
| **Backup failed / missed**, WAL archive lag > 15 min | immediately |
| TLS certificate expires in < 14 days | daily |
| OTA sync jobs in FAILED, payment webhook backlog, reporting lag | per plan thresholds |
| **Night audit not run** by the expected time; RFID terminal offline during desk hours | per schedule |

## 7. CI/CD (D-187)

**Build (on every merge and tag)** — extends the existing `ci.yml`:
- multi-stage Dockerfiles for each service (JRE base, non-root), the staff web and the landing site;
- Trivy scan, SBOM, push to **GHCR**, tagged `vX.Y.Z` + git sha.

**Release:** a tag on `main` per the git workflow (`references/git-workflow.md`). Changelog from the conventional commits.

**Staging deploy (automatic on a tag):**
- the deploy job SSHes in with a deploy key (VPS `deploy` user) → `docker compose pull && up -d` in dependency order;
- Flyway runs at service start;
- smoke tests (health + scripted API checks).

**Production deploy (manual approval by Ashish in GitHub Environments):**
- pre-deploy backup → deploy → smoke tests;
- **automatic rollback** to the previous image tags if the smoke tests fail.

**Database migrations stay backward-compatible** (expand → deploy → contract in a later release), so rolling back the images is safe. Forward-only, never edited (rule #7).

The production repo's plain source copy per release (D-142) can continue alongside, if still wanted.

## 17. Verification (when executed)
1. **Fresh provisioning:** a new VPS from the scripts → full stack healthy, HTTPS A-grade, only 80/443 public (port scan), SSH keys only.
2. **Deploy:** a tag → staging updated automatically → smoke tests pass. Production → waits for approval → backup → deploy → smoke tests. A broken image → automatic rollback to the previous tag.
3. **Backup:** WAL archiving lag < 5 min; a point-in-time restore to "10 minutes ago" on a throwaway VM matches the expected booking count; a monthly restore test is logged; a deliberately failed backup raises an alert.
4. **Monitoring:** stop a service → alert in ≤ 2 min; fill the disk to 81 % → alert; the external uptime check sees the website down when Caddy stops.
5. **Security:** ZAP baseline shows no high findings; Trivy shows no critical vulnerabilities in the images; gitleaks is clean; the permission matrix tests pass.
6. **Performance:** the k6 smoke test passes with no oversell, and p95 latency stays within the targets set in the ADR.
7. **DR drill:** "VPS lost" → rebuilt from scripts + restore within the 4 h target (timed once before go-live).
8. **UAT sign-off** received; the migration reconciliation matches the client's counts; the training attendance sheets are filed; all §26.1 documents are delivered.
