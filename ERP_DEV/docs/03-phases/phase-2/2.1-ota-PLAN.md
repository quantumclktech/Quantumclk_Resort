# Sub-phase 2.1 — OTA / Channel Management Plan (SOW ERP-09)

- Status: **Plan approved by Ashish on 2026-11-27 (docs only).** No code yet. Each work unit below still needs its own go-ahead.
- Phase: **Phase 2, the final phase** (Ashish, 2026-11-27). OTA is **sub-phase 2.1**. This numbering is the project's own and replaces the generic "Phase 3.2 / Phase 4.1" placement in the erp-prp phase template (D-144).
- Decisions: D-144 (foundation first), D-145 (one channel manager for MakeMyTrip and Booking.com). Client requests: Q-041 … Q-049.
- Audience: developers who will build ERP-02 reservations and ERP-09 OTA sync.

## Context

The SOW lists ERP-09 as a **core** module: OTA connectivity, inventory and availability sync, reservation import, cancel/modify sync "where supported by the OTA API", a channel dashboard and OTA reports. Its workflow is *OTA booking → supported API/channel → central reservation → inventory update → front office → guest communication* (`source-extracts/sow-extract.md` §12). SOW §29 says the client supplies the OTA credentials. Under the SOW exclusions, the client pays OTA commissions and subscriptions.

Client facts (`source-extracts/discovery-call-extract.md` §F, SRS §11.3):
- The channels are **MakeMyTrip and Booking.com**.
- There are "OTA rates".
- Credentials and commission are **not settled**.
- The property has **36 keys in 4 room categories**.
- No overbooking (GM override only).

**What exists today.** The codebase has `api-gateway` (:8082), `access-service` (:8091), `guest-service` (:8092) and `lead-service` (:8093, with a transactional outbox). They are Spring Boot 4.1.2 / Java 21, each with its own Postgres DB and Flyway, and use Keycloak 26. The staff web is React/Vite. Kafka is in the architecture but **not yet in `infra/docker-compose.yml`**. There are **no rooms, rates, inventory or reservations yet**, and OTA sync cannot work without them.

**Decisions**
1. **Foundation first (D-144).** Build the ERP-02 room, rate, inventory and reservation core (stage A), then the ERP-09 channel integration (stage B).
2. **Channel manager, not direct OTA APIs (D-145).** One provider-neutral integration serves MakeMyTrip and Booking.com now. A later OTA is added in the channel manager and as a mapping row, with no new code. The client chooses the channel-manager product and supplies its credentials.
   - *Rejected: direct OTA APIs.* Each OTA needs its own connectivity-partner certification, which a single property usually cannot get. It would also mean two separate builds and two maintenance burdens.

## 1. Target architecture

```
MakeMyTrip   Booking.com   (future OTAs: enable them in the channel manager)
      \          /
   CHANNEL MANAGER (client-chosen SaaS, e.g. STAAH / eZee / AxisRooms / SiteMinder)
            │  webhook + pull (reservations)      ▲ push ARI (availability / rates / restrictions)
            ▼                                     │
 api-gateway :8082  ── /api/v1/channel/webhooks/{provider} (public, signed)
            │
 channel-service  (ERP-09, NEW) ── channel_db
   ChannelManagerAdapter ← MockChannelManagerAdapter (now) / <Real>Adapter (after the client picks one)
            │  REST, client-credentials JWT, Idempotency-Key            ▲ InventoryChanged / RateChanged
            ▼                                                           │ (outbox → Kafka, or outbox polling)
 reservation-service (ERP-02, NEW) ── reservation_db  ──────────────────┘
   rooms · room types · rate plans · rate calendar · restrictions · inventory per day · reservations
            │
 web (staff ERP): Reservations ▸ Calendar · List · Inventory · Rates · OTA Management
```

- The ERP is the **source of truth** for inventory, rates and reservations. `channel-service` only translates and transports data. It never owns availability and never copies OTA availability into the ERP.
- Two services, because the Blueprint lists separate "Booking" and "External Integration" services and says to build a service only when it has a real use case. Both now have one.
- Ports: :8094 is reserved for `notification-service` (ARCHITECTURE.md §3). Fix the final ports in the ADR (unit A1), e.g. reservation :8096, channel :8097.

## 2. Stage A — Foundation: `reservation-service` (ERP-02)

The ERP's own website, walk-in and phone bookings need this too, not only OTA.

### Data model (`reservation_db`, Flyway)
| Table | Key columns / rules |
|---|---|
| `room_type`, `room` | **Owned by room-service (2.3, D-150).** reservation-service keeps only the room-type code and counts it gets from `RoomTypeCapacityChanged`; out-of-order stock arrives through the 2.3 block saga |
| `rate_plan` | code, name, meal_plan, cancellation_policy_id, channel_scope (DIRECT / OTA / MEMBER / CORPORATE), active |
| `rate_calendar` | (rate_plan, room_type, date) → amount_paise BIGINT, extra_adult_paise, extra_child_paise, currency='INR'. Money is stored in integer paise (rule #1) |
| `restriction` | (rate_plan, room_type, date) → closed, min_los, max_los, cta, ctd, stop_sell |
| `inventory_day` | (room_type, date) PK → total, sold, held, out_of_service, `version`. **CHECK (sold+held+out_of_service ≤ total + overbook_allowance)**. overbook_allowance defaults to 0 (GM override only) |
| `reservation` | id, public_ref, **source** (DIRECT, WALK_IN, PHONE, WHATSAPP, AGENT, BOOKING_COM, MAKEMYTRIP, OTHER_OTA), channel_ref (OTA booking id), guest snapshot + guest_account_id, arrival, departure, adults, children, status (HOLD, PENDING, CONFIRMED, CANCELLED, NO_SHOW, CHECKED_IN, CHECKED_OUT), total_paise, currency, rate_plan_id, **payment_collect_model** (HOTEL_COLLECT / OTA_COLLECT / VIRTUAL_CARD), payment_status, amount_paid_paise, commission_paise, net_paise, settlement_ref, version, flags (OVERBOOKED, NEEDS_REVIEW) |
| `reservation_room_night` | reservation × date × room_type (and room once allocated): this is what consumes inventory |
| `reservation_revision` | append-only before/after JSON per change, with who and source. Bookings are never silently overwritten |
| `idempotency_key`, `outbox_event`, `audit_event` | same patterns as lead-service / access-service |

### Core rules
- **Availability check and decrement happen in one transaction (rule #3).** Lock `inventory_day` rows with `SELECT … FOR UPDATE`, ordered by date to avoid deadlocks, and let the CHECK constraint guard the rest. Concurrency test: 20 parallel bookings for the last room give exactly 1 success.
- Modify means: release the old nights, consume the new nights, and write a revision, all in one transaction. Cancel releases the nights. The status machine is unit-tested.
- **An OTA booking that arrives with no stock is accepted, not rejected.** The OTA has already confirmed it to the guest. It is flagged `OVERBOOKED`, front office and the GM are alerted, and it shows on the dashboard. This is the only way stock can go below zero, and it needs `overbook_allowance` or an audit-logged override.
- Every create, modify and cancel publishes `ReservationChanged` and `InventoryChanged(room_type, dates)`. Every rate or restriction edit publishes `RateChanged`. These go through the **outbox**.
- Every create, modify and cancel accepts an `Idempotency-Key` (rule #4).

### APIs (OpenAPI, behind the gateway)
- Staff: `/api/v1/reservations/**`, `/api/v1/inventory/**` (calendar grid), `/api/v1/rates/**` (rate calendar + restrictions, bulk edit), room and room-type admin.
- Internal, called by channel-service with a client-credentials token and scope `reservations.channel`:
  - `POST /internal/v1/reservations/channel` (upsert by `(source, channel_ref, revision)`)
  - `POST /internal/v1/reservations/channel/{ref}/cancel`
  - `GET /internal/v1/ari?from&to` (availability, rates and restrictions snapshot used for full resync)

### Web
Reservation calendar (room type × date availability grid), reservation list and detail with revision history, the inventory screen, and the rates and restrictions bulk editor.

## 3. Stage B — `channel-service` (ERP-09)

### Adapter contract (the only provider-specific code, rule #16)
```java
interface ChannelManagerAdapter {
  ProviderId id();
  void pushAvailability(List<AvailabilityUpdate> u);   // mapped room type, date, count
  void pushRates(List<RateUpdate> u);                  // mapped rate plan, date, amount, occupancy
  void pushRestrictions(List<RestrictionUpdate> u);
  List<InboundReservation> pullReservations(Instant since);   // fallback / reconciliation
  InboundReservation parseWebhook(HttpHeaders h, byte[] body); // verifies the signature
  void acknowledge(String providerBookingId, AckResult r);
}
```
- `InboundReservation` is **our canonical model**: provider, ota (BOOKING_COM / MAKEMYTRIP / …), ota_ref, revision, kind (NEW / MODIFY / CANCEL), mapped room and rate codes, stay dates, guests, amounts, payment model, commission if sent, and the raw payload hash.
- **`MockChannelManagerAdapter`** is built first. It runs as an in-process fake plus a dev-only simulator endpoint that can "send" MakeMyTrip or Booking.com bookings, modifications and cancellations. It is used for development, tests and demos until credentials arrive.
- The real adapter comes later as **one class + config**. A further OTA only needs a `channel` row and a mapping. Each provider is enabled by a **feature flag** `channel.provider.<id>.enabled` (rule #15).

### Data model (`channel_db`)
| Table | Purpose |
|---|---|
| `channel_provider` | chosen channel manager, base URL, property id, **credential reference only** (secrets come from environment/secret store, never the DB or repo), enabled |
| `channel` | OTA connected through the provider: BOOKING_COM, MAKEMYTRIP (+ future), status, last_sync_at, health |
| `room_mapping`, `rate_plan_mapping` | ERP room type / rate plan ↔ provider/OTA codes. **Unmapped means the booking goes to NEEDS_REVIEW, never a guess** |
| `commission_rule` | per channel: percent or fixed, valid_from/to, tax-on-commission flag. Placeholder until the contract arrives (Q-045) |
| `inbound_message` | raw payload (PII-minimised, retention policy), provider, ota_ref, revision, **UNIQUE(provider, ota_ref, revision, kind)** for dedupe, status (RECEIVED, APPLIED, DUPLICATE, NEEDS_REVIEW, FAILED), error |
| `sync_job` | outbound ARI pushes: operation (AVAIL / RATE / RESTRICTION / FULL), date range, payload hash, status, retry_count, next_retry_at, last_error |
| `reconciliation_run` | nightly diff of ERP vs provider bookings and ARI, with discrepancies listed |
| `audit_event` | config and mapping changes, manual retries, overrides (rule #6) |

### Flows
1. **Inbound booking.**
   1. The webhook is verified (signature, and IP allowlist if the provider publishes one), stored in `inbound_message`, and answered with 200 quickly.
   2. A worker maps it. Unmapped → NEEDS_REVIEW.
   3. The worker calculates commission and net, then calls reservation-service with `Idempotency-Key = provider:ota_ref:revision`.
   4. It acks the provider. The inventory change then fans out to the other channel.
   5. A periodic `pullReservations` catches any missed webhooks.
2. **Modification or cancellation.** Same pipeline. reservation-service writes a revision and moves the nights. An out-of-order revision (older than the one stored) is recorded and skipped.
3. **Outbound ARI.**
   - `InventoryChanged` / `RateChanged` create `sync_job`s, **debounced and coalesced** (~5 s per room type and date range).
   - The worker pushes with timeouts and exponential backoff (1 m, 5 m, 15 m, 1 h, 6 h).
   - After N failures a job becomes `FAILED` (the DLQ), an admin alert is raised, and staff can retry it manually.
   - A nightly **full ARI resync** for the next 365 days fixes any drift.
4. **Scheduling (rule #19).** Spring `@Scheduled` with **ShedLock** (needs approval, Q-023), so only one instance runs each job.
5. **Event transport.** Kafka (ADR-001) if it has been introduced by then. Otherwise channel-service polls a reservation-service outbox feed (`GET /internal/v1/events?after=cursor`). Both sit behind one small interface. Decided in unit A1.

### Payments and commission (ERP-07 tie-in)
- The **collect model** is stored on each reservation:
  - HOTEL_COLLECT: the amount due goes to the folio.
  - OTA_COLLECT: the balance is an expected settlement from the OTA.
  - VIRTUAL_CARD: only the provider's token, last 4 digits and activation date are stored, **never the card number (PCI)**. Charging the card goes through the ERP-07 gateway later.
- Gross, commission and net are calculated per booking from `commission_rule`. An OTA settlement report is used to match payouts by hand. Accounting-software integration is out of scope (SOW exclusion).

### Gateway and security
- `/api/v1/channel/webhooks/{provider}`: public. The service verifies the signature, and there is an optional IP allowlist, a Redis rate limit and a body-size limit.
- `/api/v1/channel/**` (staff): role ADMIN plus a new `RESERVATIONS_MANAGER` role (the matrix is pending from the client, Decision Pack §13). Added to access-service's module/permission list. Deny by default (rule #8).

### Web: Reservations ▸ OTA Management
| Screen | What it shows |
|---|---|
| Channels | connection and health |
| Mapping editor | ERP room types and rate plans ↔ OTA codes |
| Sync Status | per channel: last push, last booking, health |
| Sync Logs | outbound pushes and inbound messages |
| **Failed Syncs** | jobs in the DLQ, with retry / resolve |
| **Needs Review** inbox | unmapped or overbooked bookings |
| Reconciliation | results of the nightly runs |
| OTA reports | bookings, cancellations and revenue by channel; commission and net |

## 5. Requests to the client (logged as Q-041 … Q-049)

1. **Which channel manager** they use or want: STAAH, eZee Centrix, AxisRooms, SiteMinder, RateGain, or none yet. The subscription is the client's cost (SOW exclusion).
2. **Channel-manager API credentials and sandbox access**: API key/secret, property/hotel ID, webhook signing secret, documentation link.
3. **Booking.com**: extranet access, Hotel ID, and confirmation that connectivity is switched to the chosen channel manager.
4. **MakeMyTrip (InGo-MMT)**: extranet access, Hotel code, and channel-manager connectivity enabled.
5. Commission % / contract terms per OTA.
6. Payment model per OTA: hotel-collect, prepaid/OTA-collect, or virtual card.
7. Room types and rate plans as sold on each OTA (for mapping), "OTA rates" vs direct rates, meal plans and taxes.
8. Cancellation / no-show policy per OTA rate plan (still unsettled: 24/48/72 h windows).
9. Overbooking (confirm zero by default, and who may override) and allocation (share all 36 rooms with every channel, recommended, or hold back an allotment).

Real credentials go only into environment/secret configuration, never into the repo or the DB.
