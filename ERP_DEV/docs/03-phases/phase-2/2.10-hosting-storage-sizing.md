# Hosting and Storage Requirements

| | |
|---|---|
| **Project** | Golden Hills Resort — Integrated Resort Management ERP |
| **Prepared by** | QuantumCLK Technologies |
| **For** | Golden Hills Resort management and QuantumCLK (server approval and budgeting) |
| **Date** | 28 November 2026 |
| **Status** | Estimate for planning. To be confirmed by a load test on staging and by real use in the first three months |

## 1. Summary

The ERP needs **one production server, one smaller staging (test) server, and off-site backup storage**:

| Resource | Production server | Staging / UAT server | Off-site backup |
|---|---|---|---|
| CPU | 8 vCPU | 4 vCPU | — |
| Memory (RAM) | **32 GB** | 16 GB | — |
| Disk | **200 GB NVMe SSD** | 100 GB SSD | **100 GB** object storage |
| Network out | about 30–50 GB per month | small | — |
| Location | data centre in India (recommended) | same | a different provider or region |

**Memory is the real limit, not disk.** The disk estimate covers about **3–4 years** of growth before it needs to be enlarged.

Hosting, domain and backup-storage charges are separate from the project fee (SOW §25.4 and §30).

## 2. What the estimate is based on

| Item | Assumption |
|---|---|
| Rooms | 36 rooms at about 60% occupancy: around **7,900 room nights** and **4,000 bookings** a year |
| Guests | about 8,000 registered adult guests a year (2 per stay) |
| Staff | about 90 users, about 30 signed in at the same time |
| Members | up to 5,000 Gold members (the membership number series), 180 booklet leaves each |
| Website | about 10,000 visits a month |
| System | about 13 application services, PostgreSQL database, Redis, monitoring tools, staff ERP and website |

If any of these is much higher (for example a second property, or far more website traffic), the numbers below need to be recalculated.

## 3. Production server disk (200 GB)

| What is stored | Year 1 | Growth per year | Notes |
|---|---|---|---|
| Database (all ERP data) | about 5 GB | +3–4 GB | Bookings, bills, payments, members, tickets. Most of the size is audit history and logs inside the database, which are kept for a set period |
| Files | about 15 GB | +8–12 GB | Guest ID scans (limited by the retention period), ticket and lost-and-found photos, payment proofs, invoice PDFs, website photos |
| Application logs (kept 30 days) | 10–20 GB | no growth | Older logs are deleted automatically |
| Monitoring data (kept 15–30 days) | 5–8 GB | no growth | Performance and health measurements |
| Application images (current + 3 older versions for quick rollback) | 10–15 GB | no growth | |
| Database working space (transaction log before it is copied off-site) | about 10 GB | no growth | |
| Message queue (only if used) | 3–5 GB | no growth | Decision pending |
| Operating system and Docker | about 10 GB | no growth | |
| **Total used** | **about 70–90 GB** | **+15–20 GB** | 200 GB keeps the disk below 70% full for 3–4 years |

A disk below 150 GB would become tight once logs and rollback versions build up.

## 4. Production server memory (32 GB)

| Part | Memory |
|---|---|
| About 13 application services | 13–16 GB |
| PostgreSQL database | 4–6 GB |
| Monitoring tools | about 2 GB |
| Message queue (only if used) | about 2 GB |
| Redis, web server, website | about 2 GB |
| Spare capacity for busy periods | the rest |

If some services are merged into one (a decision under review), memory need drops by about 2–3 GB.

## 5. Off-site backup storage (100 GB)

Backups are stored with a **different provider or region**, so they survive the loss of the main server.

| What | Size |
|---|---|
| Database copies: weekly full + daily changes, kept 30 days (compressed) | 10–15 GB |
| Continuous database change log, kept 30 days (allows restoring to any minute) | 20–30 GB |
| Files (encrypted, duplicates stored once) | about 15 GB, +10 GB a year |
| **Total** | **50–80 GB in year 1**; plan 100 GB, growing to about 150–200 GB by year 3 |

Targets: lose at most about **5 minutes** of data, and be running again within about **4 hours** after a complete server loss. A test restore is run every month.

## 6. Staging / UAT server (100 GB)

Used for client testing (UAT) and for checking every release before production. It holds **test data only**; real guest data is never copied to it. It needs less disk because logs are kept for a shorter time and fewer old versions are stored.

## 7. What changes these numbers most

1. **How long ID scans and photos are kept.** Keeping guest ID scans for 7 years instead of 90 days adds about 4 GB a year.
2. **How long audit history is kept.** Keeping it forever adds about 0.5–1 GB a year.
3. **Website traffic and photo sizes.** A CDN (content delivery network) in front of the website removes most of the bandwidth use.
4. **Message queue (Kafka) or not.** About 5 GB disk and 2 GB memory.
5. **A second property.** Roughly doubles data and file growth.

## 8. Recommended extra for higher availability (optional)

With one production server, a hardware or provider failure means the system is down until it is restored (up to about 4 hours). Bookings, payments and OTA updates stop during that time.

If the resort needs the system available outside business hours with less downtime, add a **second small server (4 vCPU, 8–16 GB RAM, 200 GB SSD)** holding a live standby copy of the database. Switching over then takes minutes instead of hours.

## 9. What we need from the resort

| # | Item |
|---|---|
| 1 | Hosting provider and region (India recommended), and who pays for it |
| 2 | Production and staging servers at the sizes above, with administrator (SSH) access for QuantumCLK |
| 3 | Off-site backup storage provider (about 100 GB to start) |
| 4 | Domain names for the website, staff ERP and API, with DNS access |
| 5 | Required uptime and support hours, which decides whether the standby server in section 8 is needed |
| 6 | How long guest ID scans, photos and audit history must be kept |

*These are planning estimates. They will be checked with a load test on the staging server and reviewed after the first three months of live use.*
