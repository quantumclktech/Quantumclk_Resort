- Status: **Plan approved by Ashish on 2026-11-27 (docs only).** No code yet. Execution order is set later in the overall execution plan.
- Phase: Phase 2 (final phase), sub-phase **2.2**. Related: [2.1 OTA plan](2.1-ota-PLAN.md), [AUTHENTICATION.md](../../02-architecture/identity/AUTHENTICATION.md).
- Decisions D-146 … D-149 · client questions Q-050 … Q-057 · change request CR-002.
- Audience: developers who will build roles, permissions and access screens for every ERP module.

> **Update 2026-11-28 (D-166, [2.0 plan](2.0-identity-auth0-PLAN.md)):** Keycloak is being replaced by **Auth0**. Where this plan says "Keycloak", read "Auth0": role bundles become Auth0 roles with `erp-api` permissions (`permissions` claim), and property/department claims come from an Auth0 post-login Action. Everything else here (catalogue, matrix, scopes, approvals, custom roles, temporary grants, audit, drift check) is unchanged.

## Context

Ashish pasted a generic RBAC plan. That plan assumes the ERP does **not** use Keycloak and proposes its own `erp_roles` / `erp_permissions` tables. The project already has working RBAC:

- **Identity:** Keycloak 26, which is itself an **OAuth 2.0 + OpenID Connect provider**. Staff are in realm `gh-staff`. Guests are in a separate realm, `gh-guests` (Blueprint §3: guests and staff never share roles).
- **Web login:** the staff web signs in with Authorization Code + **PKCE S256** (`keycloak-js`). Tokens are held in memory only.
- **Job roles:** realm roles `ADMIN`, `MANAGER` and `SALES_EXECUTIVE`. Each is a **composite** of permission client roles on `erp-api` (`employees.read`, `leads.claim`, `memberships.verify`, …). The permissions travel in the token as `resource_access.erp-api.roles`.
- **Backend:** every service validates issuer, audience `erp-api`, expiry and signature. `access-service` `SecurityConfig.authenticationConverter()` maps roles to `ROLE_x` and permissions to `PERM_x`, and endpoints use `@PreAuthorize("hasAuthority('PERM_…')")`. The check order is 401 → 403 → scope 404 → state 409 → audit (AUTHENTICATION.md §3).
- **Menu:** `GET /api/v1/me` (`MeController`) returns roles, permissions and **hard-coded** `modules()`. The web builds its menu from that.
- **Gaps:** only 3 roles against SOW §22's 10; no departments or scope model; no approval limits; no permission catalogue for the UI; custom roles and per-person grants are not designed; the module list is hard-coded.

The aim is to plan the complete ERP-wide RBAC by extending what exists, not replacing it.

## 2. Architecture

```
Staff browser ──OIDC code + PKCE S256──► Keycloak gh-staff (OAuth2/OIDC)
     │                                     realm role (job role) = composite of erp-api permission roles
     │  access token: sub, realm_access.roles, resource_access.erp-api.roles,
     │                property_id, departments (user-attribute mappers)
     ▼
 api-gateway ── validate JWT (iss, aud=erp-api, exp, sig) ──► service
                                                              │
   every service (shared erp-security library):               ▼
   1 authenticated? 401 · 2 PERM_x? 403 · 3 property/department/owner scope? 404
   4 business rule / approval policy? 409/422 · 5 audit event
                                                              │
 access-service (owner of RBAC admin):                        │
   Keycloak Admin API ◄── role & assignment changes          │
   access_db: department, employee_assignment, permission_catalog,
              custom_role, temporary_grant, approval_policy, audit_event
   GET /api/v1/me → profile, roles, permissions, scopes, modules (from catalog)
```

- **Authentication** is Keycloak's job. **Authorization** is the ERP's job, enforced in every service. The web only hides what the user can't do. Backend checks are what count.
- **When changes take effect:** a role change forces a logout (existing behaviour, S6), so new permissions apply at the next sign-in. Access tokens live 5 min (`accessTokenLifespan` 300), so a grant or revoke reaches running sessions within ≤ 5 min.
- **Token size:** about 150 permissions × ~25 bytes ≈ 4 KB, well under header limits. Measure it in R2. If it ever grows too big, switch to module-level roles plus a lookup. That is not expected.

## 6. Scope (who sees which records)

| Scope | Where it comes from | Example |
|---|---|---|
| Property | token claim `property_id` (Keycloak user attribute set by access-service, from `employee_assignment`) | every query filters by it; a mismatch gives 404 |
| Department | token claim `departments` | HK supervisor sees housekeeping tasks only |
| Own | token `sub` = record's `assigned_to` / `created_by` | housekeeper's own tasks; existing "Sales Executive: queue + own leads" |
| Field (data minimisation) | permission | ID numbers masked unless `guests.identity_read`; housekeepers see room + guest name + notes only; card data never stored |

The service never trusts a property or department sent by the client. It uses the token claims.

## 7. Approvals and separation of duties

- `approval_policy` table (access-service, config UI in R6): action → threshold in **paise** → approver permission. Examples: refund > X needs `refunds.approve`; discount > Y% needs a MANAGER; folio adjustment always needs approval; overbooking needs a GM override. **Thresholds are placeholders until the client gives them (Q-052)**. Nothing is hard-coded.
- The **request/approve records live in the owning service** (e.g. `refund_request` in billing). The rule that `requested_by ≠ approved_by` is enforced on the server. Every step is audited.
- Existing guards stay: no self-deactivation, no removing the last ADMIN (advisory lock), and a reason is required for every change.

## 9. Enforcement in code (shared across services)

- **`erp-security` shared Maven module** (needs an ADR; today each service copies `SecurityConfig`). It contains: the JWT validator + `ROLE_`/`PERM_` converter (moved from access-service), the 401/403 JSON error writers, a `Scope` helper that reads property/departments/sub from the token, and test helpers that build tokens with given permissions.
- Endpoints keep `@PreAuthorize("hasAuthority('PERM_…')")`. Scope and business rules sit in the service layer.
- **Test floor:** every permission has a test showing an allowed caller passes and a caller without it gets 403. Cross-property → 404. Housekeeper reading another's task → 404. Requester approving their own refund → 409.
- **`/api/v1/me`** returns `scopes` too, and computes `modules` from `permission_catalog` (module → permissions) instead of the hard-coded `MeController.modules()`.
- **Web:** `usePermission()`, `<Can permission="stays.checkin">`, a nav config driven by modules, a 403 page, and buttons hidden when not allowed. This is UX only.
