- Audience: developers who will build room setup, the status engine and the room board. Every other module that reads room state relies on this plan.

## Context

The room master has to come first. Reservations (2.1), front office, housekeeping, maintenance, RFID and reports all need to know what a room is and whether it is usable right now. If each module kept its own idea of room status, they would disagree. This plan gives them **one engine** that owns room facts and status changes. Every other module reads from it or sends it events.

**Client facts already known** (`source-extracts/discovery-call-extract.md`):
- 36 keys: **Premium 19 (14 queen-bed + 5 twin-bed), Suite 1, Wooden Cottages 12, Private Pool Cottages 4**.
- Occupancy is 2 adults, with 2+1 in some rooms. Extra bed costs ₹500–600.
- Statuses named on the call: *vacant/ready, occupied, dirty/cleaning, inspection, out-of-order/maintenance*.
- Reception assigns cleaning.
- If a room is not ready, the guest waits in the lounge.
- The GM approves room and overbooking exceptions.
- Inspection is **conflicting**: "no need" on one occasion, "every room, by a manager/GM" on another (C-row in the extract).
- The **dormitory** (10–12 bunks in the cottage zone) is unresolved (C-14). It must not be modelled as a 37th key.

The website already shows Premium Queen and Premium Twin as separate pages (`landing-page/.../stay-data.ts`).

**Not yet known:** room numbers, floors and buildings, connecting or accessible rooms, the client's housekeeping status sheet (requested on the discovery call), and the rules for blocks.

## 2. Where room-service sits

```
                     ┌──────────────── room-service (NEW, room_db) ─────────────────┐
 admin (setup) ────► │ categories · room types · rooms · features · settings          │
 housekeeping ─────► │ STATUS ENGINE: occupancy × housekeeping × service + flags      │
 maintenance ──────► │ blocks (OOO / OOS)  · append-only status history               │
 front office ─────► │ internal: occupancy (check-in/out) · ready-rooms query         │
                     └───┬────────────────────────────┬────────────────────────────────┘
       sync (block saga) │                            │ outbox → events
                         ▼                            ▼
       reservation-service (2.1)         RoomStatusChanged · RoomReady · RoomBlocked/Unblocked
       inventory_day.total / out_of_service    RoomTypeCapacityChanged · CleaningRequired
                         │                            │
                         ▼                            ▼
       channel-service → OTA availability     2.4 housekeeping tasks · front office · RFID · reports
```

- room-service never writes another service's database (Blueprint §2). The modules talk through REST and events only.
- Event transport: Kafka or outbox polling, whichever 2.1-A1 decides. room-service uses the same choice.
- Port and DB user: `room_db` / `room_svc`. The port is fixed in the ADR (unit M1), avoiding :8094 (notification-service).

## 3. Room master (data model, `room_db`)

| Table | Columns / rules |
|---|---|
| `room_category` | code (PREMIUM, SUITE, WOODEN_COTTAGE, PRIVATE_POOL_COTTAGE), name, sort. Used for reports only |
| `room_type` | code (PREMIUM_QUEEN, PREMIUM_TWIN, SUITE, WOODEN_COTTAGE, PRIVATE_POOL_COTTAGE), name, category_id, bed_config, base_occupancy, max_adults, max_children, max_occupancy, extra_bed_allowed, website_slug (links to the landing page), inspection_required_override (null = resort setting), sort, status ACTIVE/ARCHIVED |
| `room_feature` + `room_feature_link` | e.g. PRIVATE_POOL, JACUZZI, GARDEN_VIEW, HILL_VIEW, ACCESSIBLE, GROUND_FLOOR. Used to choose a room at assignment and for guest requests |
| `room` | number (unique), room_type_id, zone (e.g. MAIN_BUILDING, COTTAGE_ZONE), floor, connecting_room_id, notes, status ACTIVE/ARCHIVED, **occupancy**, **hk_status**, **service_status**, dnd_date, discrepancy, current_stay_ref, **version** (optimistic lock), status_changed_at |
| `room_status_history` | **append-only** (DB trigger, same as `AuditAppendOnlyTest`): room, dimension, from, to, reason_code, note, actor_sub, source (FRONT_OFFICE, HOUSEKEEPING, MAINTENANCE, SYSTEM_JOB, ADMIN), correlation_id, at (UTC) |
| `room_block` | room, kind OOO/OOS, from_date, to_date (**required**; can be extended), reason_code (MAINTENANCE, DEEP_CLEAN, RENOVATION, OWNER_USE, OTHER), note, status PENDING → ACTIVE → RELEASED / CANCELLED / FAILED, created_by, released_by, maintenance_ref |
| `room_setting` | inspection_required (default **true**), daily_dirty_time (default 06:00), timezone (Asia/Kolkata), changed_by/at. Audited |
| `job_run` | job name + business date, **unique**, so the daily job can't run twice on the same day |
| `outbox_event`, `idempotency_key`, `audit_event` | same patterns as lead-service and access-service |

Rules:
- **No hard deletes** (rule #5). A room or room type is archived. Archiving is refused if the room has a future reservation or a current stay.
- **Adding or archiving a room** recalculates the type's room count and publishes `RoomTypeCapacityChanged`. reservation-service then updates `inventory_day.total` for future dates. If the change would leave sold > total on some date, it is refused with the dates listed.
- The **dev seed** creates 36 rooms in the D-152 mix with **made-up numbers** (101…), marked dev-only and loaded only by the dev seed (same as the lead-service dev seed, D-142). Real numbers come from Q-058.
- **Dormitory:** not modelled until C-14 / Q-062 is answered.

## 4. Status engine

### 4.1 Three independent states and two flags
| State | Values | Who sets it |
|---|---|---|
| **Occupancy** | VACANT, OCCUPIED | Only check-in and check-out (front office, 2.4, via the internal API). Never set by hand |
| **Housekeeping** | DIRTY, CLEANING, CLEAN, INSPECTED | Housekeeping, the supervisor, and system events |
| **Service** | IN_SERVICE, OUT_OF_SERVICE (OOS), OUT_OF_ORDER (OOO) | Blocks only (§5) |
| Flag: DND | today's date or null | Front office or housekeeping, when the guest asks for no service |
| Flag: discrepancy | none / SKIP (system says occupied, room looks empty) / SLEEP (system says vacant, room is in use) | Reported by housekeeping, resolved by front office with a reason |

- **OOO** = taken out of sellable stock for the block's dates (inventory decreases). Used for repairs and renovation.
- **OOS** = stays in stock, but can't be assigned until it is fixed. Used for short problems (e.g. the AC is being checked today).

### 4.2 Overall status (worked out from the states, not stored)
| Code | Meaning | Condition |
|---|---|---|
| **READY** | can be given to a guest | VACANT + IN_SERVICE + (INSPECTED, or CLEAN when inspection is off) |
| VC | vacant clean, waiting for inspection | VACANT + CLEAN + inspection on |
| VD | vacant dirty | VACANT + DIRTY/CLEANING |
| OC / OD | occupied clean / dirty | OCCUPIED + CLEAN/INSPECTED or DIRTY/CLEANING |
| OOS / OOO | blocked | service ≠ IN_SERVICE (this overrides the other codes) |

One function, `RoomStatus.derive(...)`, works this out. It is used by the API, the board and the events, so they never disagree.

### 4.3 Allowed changes (anything else → **409 INVALID_TRANSITION**)
| From → To | Trigger | Permission (2.2) | Rule |
|---|---|---|---|
| any → DIRTY | check-out event | system | always; publishes `CleaningRequired` |
| CLEAN/INSPECTED → DIRTY | daily job (occupied, no DND today) | system | once per business date (`job_run`) |
| DIRTY → CLEANING | housekeeper starts | `housekeeping.tasks_complete` | own assigned room once 2.4 exists; any room before that |
| CLEANING → CLEAN | housekeeper finishes | `housekeeping.tasks_complete` | if inspection is off, the room becomes READY and `RoomReady` is published |
| CLEAN → INSPECTED | supervisor or GM passes it | `housekeeping.inspect` | `RoomReady` is published if the room is vacant and in service |
| CLEAN → DIRTY | inspection fails | `housekeeping.inspect` | reason required |
| INSPECTED → DIRTY | room used again, or a guest complaint | `rooms.status_update` | reason required |
| any → any (housekeeping) | manual correction | **`rooms.status_override`** (new, sensitive; MANAGER/GM) | reason required, audited, shown in history |
| VACANT → OCCUPIED | check-in | system (front office) | room must be READY, unless the GM override is passed (Q-064), which is audited |
| OCCUPIED → VACANT | check-out | system (front office) | sets DIRTY at the same moment |

- Each change is **one request**: `POST /rooms/{id}/transitions {dimension, to, reasonCode?, note?, expectedVersion}`. A stale `expectedVersion` → 409 STALE, so two people tapping the same room can't overwrite each other.
- Each change writes the room row, a history row, an audit row (for sensitive changes) and an outbox event **in one transaction**.
- The change table lives in code as data (a list of rules). One parameterised test checks every pair, allowed and refused.

## 5. Blocks (OOO / OOS) and room stock

**OOO block saga** (keeps OTA stock correct without a distributed transaction):
1. room-service creates the block as `PENDING`.
2. room-service calls reservation-service `POST /internal/v1/inventory/out-of-service {roomType, from, to, +1, blockId}`. The call is idempotent by blockId, and the stock update is the same locked one as in 2.1.
3. reservation-service refuses the call if a date would end up with sold > sellable (**409 with the dates**). The block becomes `FAILED`, and the user is told to move bookings or ask for the GM overbooking override.
4. On success the block becomes `ACTIVE`. From its from_date the room's service status is OOO. `RoomBlocked` is published, and the 2.1 channel-service pushes the new availability to the OTAs.
5. **Release** (manually, or automatically after to_date) gives the stock back through the same call with −1. The room returns to IN_SERVICE with housekeeping status **DIRTY** (it needs cleaning after the work). `RoomUnblocked` is published.

More rules:
- **OOS** blocks don't touch stock. They only stop the room being assigned. Front office sees a warning.
- A room can't be blocked while it is OCCUPIED for today. Move the guest first (2.4).
- A future block that overlaps a booking **already assigned to that room** is allowed, but the booking is flagged "needs reassignment" for front office.
- Blocks can be extended (a new stock call covers only the extra dates). Overlapping blocks on the same room are refused.
- A failed or stuck PENDING block is retried by a job and appears on the board as "Block pending".

## 6. APIs (OpenAPI, behind the gateway; permissions from 2.2)

| Method & path | Use | Permission |
|---|---|---|
| `GET /api/v1/rooms?type&zone&floor&status&ready` | list / board data | `rooms.read` |
| `GET /api/v1/rooms/board` | counts per derived status + tiles (one call for the board) | `rooms.read` |
| `GET /api/v1/rooms/{id}` · `/history` | detail and timeline | `rooms.read` |
| `POST /api/v1/rooms/{id}/transitions` | status change (§4.3) | per the change |
| `POST /api/v1/rooms/{id}/dnd` · `/discrepancy` · `/discrepancy/resolve` | flags | `rooms.status_update` |
| `GET/POST /api/v1/room-blocks`, `POST /room-blocks/{id}/extend` · `/release` · `/cancel` | blocks | `rooms.block` |
| `GET/POST/PUT /api/v1/room-types`, `/rooms`, `/room-features` (+ `/archive`) | setup | `rooms.configure` |
| `GET/PUT /api/v1/room-settings` | inspection setting, daily time | `settings.resort_manage` |
| `GET /internal/v1/rooms/ready?type&from` | front office assignment (2.4) | service token |
| `POST /internal/v1/rooms/{id}/occupancy {checkIn/checkOut, stayRef}` | idempotent by stayRef | service token |
| `GET /api/v1/portal/room-types` | public room-type facts for the booking engine (later plan) | none (read-only, rate-limited) |

Errors use the existing `ApiError` shape: 400 validation, 403, 404 (not in scope), **409 INVALID_TRANSITION / STALE / BLOCK_CONFLICT**.

## 9. Events (the contract for 2.1, 2.4, RFID and reports)

| Event | Key fields | Consumers |
|---|---|---|
| `RoomTypeCapacityChanged` | roomType, activeRooms, effectiveFrom | reservation-service (`inventory_day.total`) |
| `RoomStatusChanged` | roomId, number, dimension, from, to, derived, source, at | board/reports, RFID (later) |
| `RoomReady` | roomId, roomType, at | front office: "room ready" for a waiting guest (lounge case) |
| `CleaningRequired` | roomId, reason (CHECKOUT, DAILY, FAILED_INSPECTION, AFTER_BLOCK) | 2.4 housekeeping tasks |
| `RoomBlocked` / `RoomUnblocked` | roomId, kind, from, to, blockId | front office, reports (OTA stock goes through the saga) |

Events carry ids and codes only, no guest personal data. Consumers must be idempotent (Blueprint §2).
