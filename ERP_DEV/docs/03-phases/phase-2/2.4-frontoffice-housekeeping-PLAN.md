## Context

2.1 creates reservations and 2.3 tracks room status. This plan covers what reception and housekeeping do between those two: **arrival → ID check → room assignment → check-in → stay changes → check-out**, and **cleaning tasks → inspection → room ready → reception sees it** (SOW §19 workflow).

**Client facts** (`source-extracts/discovery-call-extract.md` §B, §D; summary §3.3–3.4):

| Topic | Fact |
|---|---|
| Check-in / check-out | Check-in **12:00**. Check-out **11:00**, but the AM/PM is unclear (C-13). About 1 hour turnaround |
| Early check-in / late check-out | "Dynamic, subject to availability"; management can adjust the charges |
| Room not ready | The guest **waits in the lounge**; room transfer is supported |
| No-show | Paid bookings are non-refundable; unpaid tentative bookings are cancelled (derived SRS) |
| ID | **Aadhaar or driving licence** (voter ID in the SRS); no webcam capture at reception |
| Exceptions | The GM approves room and overbooking exceptions |
| Housekeeping | Front desk/reception assigns cleaning tasks and priorities; supervisor or GM inspection (configurable, D-151) |
| Raised, rules unclear | VIP / priority room, lost & found, minibar |

## 1. Decisions (D-154 … D-157)

| ID | Decision | Why |
|---|---|---|
| D-154 | **Stays live in `reservation-service`.** A stay is the next stage of the same reservation: check-in, room assignment, transfer, extension and check-out. **Room assignment** is a database rule on (room, night), next to the bookings, so a room can never be assigned twice for the same night. Front office screens call reservation-service, which tells room-service about occupancy. | Ashish chose the recommended option. Stops double assignment without cross-service locking. |
| D-155 | **Housekeeping tasks live in `room-service`**: tasks, assignment, priority, progress, minibar reports and lost & found. Starting or finishing a task changes the room status (2.3) **in the same transaction**. | Ashish chose the recommended option. Task and room status can't disagree, and there is one fewer service. |
| D-156 | **Guest ID at check-in:** store the **masked number + keyed HMAC hash** (same as members, D-131). Optionally store **one uploaded scan**, encrypted with AES-256-GCM (same as `ProofStorage`), viewable only with `guests.identity_read` and **deleted after a retention period the client sets** (Q-067). No webcam capture. | Ashish chose the recommended option. Covers the guest register, Form C and audits while holding as little data as possible (DPDP). |
| D-157 | **Check-out is blocked unless settled.** Settled means a zero balance, or **bill to company / OTA prepaid**, or a **GM override** with a reason (audited). Until 2.5 is built, check-out records `settlement: PENDING` through a `FolioPort` stub, and the real check plugs in later. | Ashish chose the recommended option. Revenue isn't lost at the desk. |

## 3. Part A — Front office (reservation-service)

### 3.1 Stay lifecycle
The 2.1 reservation statuses are extended to:

```
CONFIRMED ──arrive──► ARRIVED (registered, waiting for room) ──check-in──► CHECKED_IN ──check-out──► CHECKED_OUT
    │                         ▲ (skip ARRIVED when the room is ready)          │
    ├──night audit──► NO_SHOW │                                               └─ extend / shorten / transfer (stay stays CHECKED_IN)
    └──cancel──► CANCELLED
```

- **ARRIVED** covers the *guest waits in the lounge* case. Registration and the ID check are done, but the room isn't READY yet. When room-service publishes `RoomReady` for the assigned room (or any READY room of the type), the desk gets an alert ("Room 104 ready for Mr X") and completes check-in.
- Each change writes a `reservation_revision` (2.1), an audit row and an outbox event, in one transaction.

### 3.2 New data (reservation_db)
| Table | Purpose |
|---|---|
| `reservation_room_night.room_id` | the assigned room per night. **Exclusion constraint:** a room has at most one reservation per night while the reservation is active (not CANCELLED/NO_SHOW) |
| `stay_registration` | one row per adult guest: name, mobile, nationality, address, purpose of visit, **id_type** (AADHAAR, DRIVING_LICENCE, VOTER_ID, PASSPORT), **id_masked**, **id_hash**, scan reference (encrypted file, optional), Form C fields for foreign guests (passport no. masked, visa, arrival from, next destination), signed_at. No full ID number is stored (D-156) |
| `stay_event` | arrival, check-in and check-out times (actual vs scheduled), early/late flags, who did it |
| `room_move` | reservation, from_room, to_room, at, reason_code (GUEST_REQUEST, MAINTENANCE, UPGRADE, OVERBOOKING), rate_effect, actor |
| `business_date` | the current hotel business date (Asia/Kolkata) + night-audit runs |
| `front_desk_setting` | check-in time (12:00), check-out time (11:00, Q-065), early/late windows, no-show rules (Q-069), night-audit time (placeholder 03:00), ID-scan retention days (Q-067) |

### 3.3 Arrival and check-in
1. **Find the booking** on the arrivals list (today's business date), by name or reference, or by scanning the confirmation (later).
2. **Register each adult.** Choose the ID type. The number is checked by `IdentityNumbers` (reused from membership) and stored masked + hashed. An optional ID scan is uploaded (JPEG/PNG/PDF, checked by magic bytes, ≤ 5 MB, encrypted). Foreign guests fill the **Form C fields**, and the ERP produces a printable Form C sheet; submitting it on the FRRO portal is manual (a portal integration would be a CR).
3. **Assign a room** (§3.4). If the room isn't READY, the booking becomes **ARRIVED** and the guest waits.
4. **Check in.** reservation-service asks room-service whether the room is READY, then commits CHECKED_IN + outbox in one transaction. After that it sends occupancy to room-service with retries, idempotent by stayRef. If the room is not READY, check-in is refused unless a **GM override** with a reason is given (Q-064, audited).
5. **Early check-in** (before 12:00) is allowed if the room is READY. Any charge comes from settings and is posted through `FolioPort` (2.5). Waiving the charge needs approval (2.2 approval policy).
6. **Payment at check-in** (advance or balance) goes through `FolioPort`. In 2.4 it is only shown; collection is built in 2.5.

### 3.4 Room assignment
- Only a room of the **booked type**, unless it is an **upgrade**: reason required, `rooms.assign` + `reservations.modify_rate` if the price changes, audited.
- The room must be free for **every night** of the stay (the exclusion constraint) and must not be OOO/OOS on those dates (2.3).
- **Pre-assignment** for future arrivals is allowed for rooms that aren't READY yet. The arrival list then shows "assigned · not ready".
- **Suggestion order** (the user can always choose differently): features the guest asked for (from the booking notes or preferences) → READY now → VIP priority → same zone as linked bookings / connecting rooms → least recently used (spreads wear across rooms).
- A 2.3 block on an assigned room flags the booking **needs reassignment** on the dashboard.

### 3.5 During the stay
| Action | Rules |
|---|---|
| **Room transfer** | The new room must be READY and free for the remaining nights. The old room → DIRTY (via room-service). Reason required. If the room type changes, any rate change needs `reservations.modify_rate` |
| **Extend stay** | Stock check for the extra nights (2.1). If the same room is taken on those nights, the desk is offered a transfer |
| **Shorten stay / early departure** | Releases the unused nights and stock. Any charge follows the cancellation policy (2.5) |
| **Late check-out** | A request is approved by a manager if the room has an arrival that day. The charge comes from settings (2.5) |
| **VIP / special requests** | A VIP flag and notes on the reservation. These give the room priority in housekeeping tasks and can create a "welcome amenity" task (Q-071) |

### 3.6 Walk-in
One screen, one flow: check availability (2.1) → create a reservation with source **WALK_IN** → register (ID) → assign a READY room → check in. Payment or advance is collected through `FolioPort` (2.5). It uses the same rules and audit as any booking.

### 3.7 Check-out
1. The **due-outs list** shows today's departures. Rooms past check-out time are highlighted (late).
2. **Settlement check** (D-157): `FolioPort.balance(stay)` must be 0, or the bill must be **bill to company / OTA prepaid** (2.1 payment model), or a **GM override** with a reason must be given. Until 2.5: the result is `PENDING` and check-out goes ahead with the stay marked *settlement pending*. When 2.5 arrives it enforces the rule, with no front-office change.
3. Commit CHECKED_OUT → room-service sets the room VACANT + DIRTY → a `CleaningRequired(CHECKOUT)` task is created.
4. Reports and guest history get the actual times. A feedback or loyalty hook is left for ERP-05/ERP-13.

### 3.8 Night audit (end of day)
- Runs at the configurable time (placeholder 03:00 IST) with ShedLock. A MANAGER can also run it from the screen, which shows a checklist. It runs once per business date (`business_date` row).
- Steps:
  1. **No-shows:** arrivals not checked in → NO_SHOW. A paid booking keeps its charge per policy; an unpaid tentative one is cancelled (Q-069). Stock is released.
  2. List **due-outs not checked out** and **ARRIVED guests still waiting**, for the morning shift.
  3. Post the room-night charges through `FolioPort` (active from 2.5).
  4. **Roll the business date**.
  5. Produce the night-audit report.
- The 2.3 daily cleaning job (06:00) stays separate. It belongs to housekeeping, not accounting.

### 3.9 Front-desk dashboard (staff web)
| Section | Content |
|---|---|
| Today strip | Arrivals (assigned / unassigned / ready), In-house, Departures, Late due-outs, ARRIVED-waiting, Rooms ready count (from 2.3) |
| Arrivals list | Booking, guest, type, assigned room + its status, VIP, source (OTA badge), actions: Register / Assign / Check in |
| In-house list | Room, guest, nights left, actions: Transfer / Extend / Late check-out / Check out |
| Alerts | `RoomReady` for waiting guests · OVERBOOKED (2.1) · needs reassignment (2.3) · settlement pending |
| Quick actions | **Walk-in**, guest/booking search, room board (2.3) |

## 4. Part B — Housekeeping (room-service)

### 4.1 Tasks
| Field | Values / rule |
|---|---|
| `hk_task.type` | CHECKOUT_CLEAN, DAILY_SERVICE, TOUCH_UP, DEEP_CLEAN, AFTER_BLOCK_CLEAN, INSPECTION, WELCOME_AMENITY (task types are a setting, Q-070) |
| status | OPEN → ASSIGNED → IN_PROGRESS → DONE → (INSPECTED / FAILED → reopened) · CANCELLED |
| priority | **worked out automatically**: arrival today for this room or type → HIGH; VIP → HIGH; ARRIVED guest waiting → URGENT; otherwise NORMAL. Reception or the supervisor can raise it, with a reason |
| assignee | one housekeeper. Assigned by **reception or the HK supervisor** (client: reception assigns; Q-070) |
| times | created, assigned, started, finished, inspected; duration for reports |

- **Created automatically** from 2.3 `CleaningRequired` events (check-out, daily, failed inspection, after a block). Created by hand for touch-up, deep clean or amenity. Duplicate tasks are prevented: one open cleaning task per room.
- **Start** = 2.3 change DIRTY → CLEANING. **Finish** = CLEANING → CLEAN (or READY if inspection is off). Both happen **in one transaction** with the task (D-155).
- **Inspection** (when on): the task appears in the 2.3 inspection queue. Pass → INSPECTED / READY. Fail → reason + checklist items → task reopened, room DIRTY.
- **Checklist** per task type (optional, configurable; the client's housekeeping status sheet, Q-058/Q-070).
- **Assignment helper:** shows open tasks by zone and each housekeeper's current load, and suggests the least-loaded housekeeper in the same zone. No automatic assignment unless the client asks.

### 4.2 Minibar and lost & found
| Feature | Design |
|---|---|
| **Minibar report** | While cleaning, the housekeeper records items used from a configurable **item list with prices** (Q-070). This publishes `MinibarConsumed(stayRef, items)`, which 2.5 posts to the folio. Front office sees it on the stay before check-out |
| **Lost & found** | Item log: found_in (room/area), found_by, description, photo (optional, encrypted), linked stay if known, storage place, status FOUND → STORED → RETURNED (to whom, ID checked) / DISPOSED (after the retention days, Q-070). Audited |

### 4.3 Screens
| Screen | Who |
|---|---|
| **HK dashboard**: tasks by status and zone, rooms waiting for inspection, urgent rooms (guest waiting), staff load | HK supervisor, reception |
| **Assign board**: drag or select tasks to housekeepers | reception, HK supervisor |
| **My tasks (phone)**: list in priority order, Start / Finish, checklist, minibar entry, "Found item", "Report issue" (→ maintenance, later plan) | housekeeper |
| **Lost & found register** | HK supervisor, reception |
| **HK reports**: rooms cleaned per person per day, average clean time per task type, inspection fail rate, open tasks ageing | HK supervisor, managers |

## 9. Verification (when executed)

1. **Assignment safety:** 10 parallel requests to assign room 104 for overlapping nights → exactly one succeeds. Extending into a night where the room is taken → transfer offered, never a double assignment.
2. **ID privacy:**
   - the DB holds only the masked number and the hash;
   - the scan is encrypted at rest and refused (403) without `guests.identity_read`;
   - the retention job deletes scans after N days;
   - logs and events contain no ID numbers.
3. **Lifecycle:**
   - **waiting guest:** arrive with the room dirty → ARRIVED; housekeeper finishes, supervisor passes → `RoomReady` alert → check-in succeeds;
   - **override:** check-in to a dirty room without the override → 409; with the override → audited;
   - **check-out:** check-out → the room is VD and a CHECKOUT_CLEAN task is created automatically.
4. **Night audit:** an unarrived paid booking → NO_SHOW and stock released; running it twice on the same date → no double effect; the business date rolls at the IST time.
5. **Housekeeping:**
   - a housekeeper can't see another person's task (404);
   - Start/Finish keeps the task and the room status in step even if one write fails (single transaction);
   - a VIP or waiting-guest room gets HIGH/URGENT priority.
6. **Check-out rule:** with the 2.5 stub → settlement PENDING recorded. With a fake balance > 0 in tests → 409 unless a GM override is given.
7. **Permission tests** for every endpoint. Live demo on the dev seed: walk-in → check-in → minibar entry → transfer → check-out → cleaning → inspection → READY.
8. All service tests, web tests, lint and build pass.
